# Fix plan: memory growth and lifecycle audio interruptions

Status: implementation completed in the working tree with automated verification. See [implementation results](2026-09-05-implementation.md). Installation, live hardware waveform/peak validation, and any further seamless-topology work remain outstanding.

Evidence: [investigation](2026-09-05-memory-and-audio.md). Goal: bounded BAMStreamDeck memory and uninterrupted playback for unrelated app launches/exits, while retaining protection against full-volume bursts. Genuine routing changes have a separate measurement gate below.

## Non-negotiable safety contract

- Keep hardware mute before every actual or uncertain tap/aggregate mutation, including startup, permissions, recovery, and errors.
- Never call the current `startRouter` as a dry-run: it mutates taps before its aggregate-signature check.
- Skip hardware writes only for a proven healthy, unchanged resolved route. Preserve master mute and output-switch fade ownership.
- Use existing serialization; preflight decisions cannot outlive the state they checked.
- No new dependencies, driver rewrite, fixed-UID change, or overlapping tap/aggregate creation in this fix.

## 3. Avoid guard entry for healthy routing no-ops

Files expected: `BamKit/Sources/AudioEngine/CoreAudioEngine.swift`, `BamKit/Sources/BamCore/AudioEngineProtocol.swift`, `BamKit/Sources/BamCore/MockAudioEngine.swift`, `App/ConsoleViewModel.swift`, `App/ConsoleViewModel+Volume.swift`, existing recovery/event tests.

Extract the existing route-resolution/signature decision ahead of tap mutation. Compute the resolved output/capture devices, grouped process membership, remainder exclusions, and relevant routing state once. Compare with the successfully running route, including health/force-recovery state. Missing or ambiguous information means guarded reconciliation.

The engine owns topology knowledge; the view model owns hardware guarding. Prefer a read-only `canKeepCurrentRouter(config:) async -> Bool` used only for event reconciliation, with conservative `false` fallback. Extract one pure desired-tap specification helper reused by this check and `startRouter`, avoiding independent signature algorithms in engine and UI.

A `true` result permits only **doing nothing** to audio; it never authorizes an unguarded later mutation. A `false` result enters the existing mute guard first, then re-resolves fresh state and performs the guarded start. Do not export prepare/apply tokens or carry a stale topology snapshot across actor suspension. Strict equality with the successfully applied config is a conservative starting gate; healthy live topology and device identity checks are additionally required. Manual restart, startup, heartbeat recovery, and permission/rearm paths do not use the bypass.

Health must be tied to the current router generation and a recent clean observation from the existing health loop, including current format/device validity. `hasAdvancedIO` alone only proves a callback ran in the past. Invalidate eligibility at start, teardown, suspected failure, permission wait, and recovery pause; unknown health returns false. Ensure a newly started router eventually becomes eligible after verified healthy observations so self-generated notifications settle. Add pure topology predicate tests in `BamKit/Tests/AudioEngineTests/RouterTopologyTests.swift` and mock-backed event tests in `AppTests/RouterRecoveryTests.swift`.

Route event reconciliation through the existing serialized router-work path. Read current state when the operation executes. For a healthy no-op, keep UI/device discovery current but do not mute, change hardware volume, recreate taps, or restart I/O. For any real change or recovery, retain the existing mute-before-mutation sequence and failure behavior.

Acceptance: unrelated process/device events with unchanged resolved topology perform zero hardware mute/volume writes and zero tap/aggregate mutations. Explicit recovery of an unhealthy router with the same signature still rebuilds under protection.

### 3a. Repair recovery guard ordering before enabling the bypass

Additional planning inspection found `CoreAudioEngine.recoverRouterAfterHealthFailure:697-702` clears taps/router before the guard at 705, the paused branch tears down at 691, and `retryAfterRearm:730` starts directly. This is source evidence of a guard-order gap, not a reproduced current volume blast.

Move protection ahead of every destructive recovery operation, including pause/teardown and rearm. Inspect all `startRouter`/tap-release callers, not just the lifecycle path. Define the recovery result so output is restored/unmuted only once a safe muted-tap/attenuated route is established. On unsafe partial failure or unsuccessful mute, avoid destructive continuation or unguarded restoration; keep a recoverable safe state. Preserve the original saved volume/mute across nested recovery attempts rather than capturing temporary protection as the user's intended state. Prefer extending existing guard/result handling over introducing a second competing guard owner.

Add order-sensitive tests for successful recovery, exhausted retry pause, rearm, failed tap/aggregate creation, missing output, and guard-write failure before implementation. A no-op optimization must not ship while its recovery fallback can mutate unprotected.

Current device mute setters discard write results, so a call recorder alone cannot prove protection succeeded. Extend existing device operations/guard result handling minimally to distinguish applied, unsupported, and failed protection. Verify successful main-channel or complete channel protection as appropriate for the device; on failure, abort destructive work while preserving the existing route and report failure. Confirm volume restoration before unmuting. Capture intended per-device volume/mute once before the first guarded operation and retain it through failed retries; do not recapture a transient mute or HAL-reset maximum as the user's target. Keep explicit user changes and output-switch ownership coherent.

Exercise actual engine recovery/teardown paths through existing device-operation test hooks, extending them narrowly where needed. View-model mocks alone cannot detect the pre-guard teardown defects. The engine helper currently accepts a Void rebuild and unconditionally restores/unmutes; replace that assumption with an explicit safe-result check.

## 4. Collapse redundant event work

Files: `CoreAudioEngine.swift`, `ConsoleViewModel.swift`, existing router event lifecycle/recovery tests.

Treat notifications as current-state invalidations, using newest-only pending buffering where events have no unique payload that must be replayed. Serialize reconciliation and ensure a notification arriving during work triggers a subsequent pass against latest state. Preserve cancellation/listener teardown. Start with `bufferingNewest(1)` rather than a new timer/debounce service. Add a delay only if measured burst behavior still requires it.

Acceptance: an event burst converges to the latest process/device state with bounded pending work; a final real device/PID change is not lost. Recovery and user output-switch operations remain ordered and protected. Notifications generated by a rebuild must settle without repeated guard cycles once the route is healthy.

## 5. Lock down safety and validate hardware

Tests: extend `AppTests/RouterRecoveryTests.swift`, package router lifecycle/guard tests, and existing mocks with ordered operation recording where needed.

| Scenario | Required behavior |
| --- | --- |
| Healthy unchanged topology, repeated process/device event | No hardware writes, tap changes, or restart |
| Grouped app/helper PID set or remainder exclusions change | Mute before first tap/aggregate change |
| Output/capture change, unplug/replug, same UID with new object identity | Re-resolve; guard any real/uncertain change |
| Startup, capture permission retry, unhealthy same-signature recovery | Guard preserved; no false no-op |
| Tap/aggregate failure or cancellation | Safe-state result checked before restore/unmute; no assumed baseline failure safety |
| Master already muted | No unintended unmute during restore |
| Event during user output switch/edit | Serialization prevents stale preflight and interleaved restore |
| Notification during reconciliation / event burst | Latest state eventually reconciled; bounded queue |

Run targeted tests first, then `make test` for package plus app/recovery suites and normal build checks. Existing baseline was 60 XCTest cases (2 hardware skips) and 34 Swift Testing cases passing; those results do not validate new fixes. Any hardware skips remain explicit gaps until the measured checks below run.

With controlled playback, record waveform continuity and peak levels at mixed source gains and with muted sources. Compare unrelated app launch/exit, grouped helper churn, default/output changes, and recovery. Use existing rebuild/create signposts to correlate gaps. Do not increase user hardware volume, remove guarding, or alter routing merely to make a test convenient. Use a controlled capture/loopback setup for peak-output validation before relying on audible listening.

## 6. Real topology changes: measure before expanding the fix

The existing shared aggregate teardown and 2048-frame startup fade cause intentional interruption when grouped process membership actually changes. Steps 3–4 remove unnecessary work but do not promise seamless real rebuilds.

After those fixes, measure remaining grouped-app gaps and peak levels. If user-visible glitches remain, validate whether the chosen Core Audio APIs support safely updating live tap membership/aggregate state without teardown. That needs a separate bounded prototype, current primary API evidence, and safety tests before adopting it. Retain guarded break-before-make unless the replacement proves no bypass audio, no UID conflicts, and correct exclusion behavior. Do not declare the entire glitch issue resolved if those interruptions still violate the desired behavior.
