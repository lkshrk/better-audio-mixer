# Dynamic audio membership and full-volume bypass

## Conclusion

Keep one persistent hardware-clocked output aggregate and persistent taps per configured **source**, then change membership inside those taps. Ordinary application launches/exits should not stop the output IOProc, replace the aggregate, reset gain ramps, or reset the limiter. Chromium provides a concrete implementation precedent for updating a running tap's process membership.

This is the best first prototype, not yet a verified safety fix. Independently protect against direct original playback and the first sound of a newly launched process. On macOS 26, persistent bundle-ID subscriptions are promising. If process taps cannot demonstrate that protection, use a persistent virtual-output architecture with per-client attenuation before mixing.

The user's actual setup is hardware/headset volume at 100%, with attenuation in individual BAM channels. Their v1.0.5 full-volume burst report supersedes the previous low-volume listening result. Earlier Calculator cycles did not exercise grouped audio-process membership. Zero limiter failures cannot detect audio that bypasses the limiter. The release has an unresolved safety regression for this setup.

Research was read-only: no device probes, playback experiments, routing changes, restarts, or implementation edits.

## What the current implementation establishes

1. **Membership changes force shared rebuilds.** `CoreAudioEngine.swift:602–632` includes process AudioObjectIDs in tap signatures, omits configured sources with no running processes, and builds the remainder exclusion list from currently grouped processes. Changed signatures create new taps at `:768–784`; the aggregate signature contains tap UUIDs at `:809`. The replacement path at `:827–855` closes the aggregate and creates another.
2. **Tap lifetime is not equivalent to original-output suppression.** Every desired tap uses `.mutedWhenTapped` (`CoreAudioEngine.swift:614`). Apple's enum contract ties this suppression to reading the tap. The existing comment at `:820–825` claiming retained taps make the swap safe overstates what is guaranteed. Stopping the reader matters even if its tap objects survive. [Apple mute behavior](https://developer.apple.com/documentation/coreaudio/catapmutebehavior)
3. **Accepted hardware writes are treated as completed protection.** `checkedDeviceWrite` at `CoreAudioEngine.swift:495–509` and `CA.setUInt32` at `CoreAudioProperty.swift:112` return success from the setter. `protectOutputs` at `ConsoleViewModel+Volume.swift:159–175` proceeds on that result. Apple's SDK explicitly warns that many property changes are asynchronous and must not be considered completed before listener notification. Install scripts performed extra readbacks; normal runtime protection does not use that installer sequence. [Apple property setter](https://developer.apple.com/documentation/coreaudio/audioobjectsetpropertydata(_:_:_:_:_:_:))
4. **Start success is not confirmed capture readiness.** `RouterAggregate.startIO` returns `AudioDeviceStart` status (`RouterAggregate.swift:439–454`). The engine then returns `.ok`; the App restores hardware mute state (`ConsoleViewModel+Volume.swift:121–152`). It does not wait for the new callback's valid input/output or confirmation that original playback is suppressed. The health monitor starts later. `DeviceIsRunning` alone is insufficient: Apple's SDK allows it to be true without an active IOProc. [Apple AudioDeviceStart](https://developer.apple.com/documentation/coreaudio/audiodevicestart(_:_:))

These are concrete control-flow and contract gaps, consistent with the reported bypass. They do **not** identify the exact acoustic onset of the user's burst; that requires output-side measurement. New atomic gains and gain ramps initialize at zero, so a newly initialized unity gain is not the explanation found here.

## Supported mechanisms and tradeoffs

| Mechanism | Evidence | Assessment |
| --- | --- | --- |
| Update an existing tap description/process list | Apple documents `kAudioTapPropertyDescription` as modifiable. Chromium writes a new process list on its existing active tap. | First compatibility prototype: retain tap IDs/UUIDs, aggregate, IOProc and fixed input layout. A supported property update is not a guarantee of atomic or inaudible handoff. |
| Subscribe by bundle ID | `CATapDescription.bundleIDs`, macOS 26+. | Preferred experiment for configured applications: let HAL follow process lifetime without PID-driven replacement. Verify first-launch behavior, empty sources, exclusions and helper processes. |
| Enable process restoration | `isProcessRestoreEnabled`, macOS 26+. | Remembers applications previously tapped and restores them after restart. Do not equate it with admission of every never-seen process before its first sound. |
| Change aggregate TapList live | Apple's sample sets `kAudioAggregateDevicePropertyTapList`. | Reserve for actual source configuration changes. BAM's callback freezes input indices/channel mapping. Changing HAL membership alone could apply another source's gain to an input. Requires explicit layout validation and safe render-state publication. |
| Separate aggregate per application | FineTune does this and retains controllers briefly through transient disappearance. | Reduces the scope of disruption, but affected-app teardown still exists. More IOProcs/resources and a less direct shared final-limiter path; not the first choice. |
| Persistent virtual output with per-client attenuation | Background Music's HAL driver tracks clients and applies gain before the mixed output. | Stronger routing boundary for applications using the virtual device. Larger driver/control/clocking change; direct hardware selection can still bypass it. |

Apple references: [tap description](https://developer.apple.com/documentation/coreaudio/kaudiotappropertydescription), [bundle IDs](https://developer.apple.com/documentation/coreaudio/catapdescription/bundleids), [process restoration](https://developer.apple.com/documentation/coreaudio/catapdescription/isprocessrestoreenabled), [tap/aggregate sample](https://developer.apple.com/documentation/coreaudio/capturing-system-audio-with-core-audio-taps).

Local SDK evidence: `CoreAudio.framework/Headers/AudioHardware.h` around lines 302–304 and 2015–2017; `CATapDescription.h` around lines 26–28, 131–136 and 162–168 in the installed macOS SDK. The repository supports macOS 14.4; bundle properties require an availability branch or an explicit minimum-version decision. API presence is verified; seamless behavior is not.

## Why simply changing the mute enum is not enough

`.muted` is intended to suppress original output independently of ongoing reads, making it worth testing for protection that survives a reader restart. But the `catap` project's documented listening experiment reports that suppression began only after an aggregate containing the tap was created, not at bare tap creation. It then persisted after recording stopped. This is an empirical project report, not a universal guarantee. [Pinned experiment](https://github.com/sbetko/catap/blob/f8d2c4aa9644038e34816a5c887a02f896516e22/docs/mute-behavior.md)

A permanent global excluding-self mute guard, separate from processing membership, is therefore a **research candidate**, not a proven one-line fix. Initialization, overlapping taps, new-process coverage and teardown must all be measured. Hardware mute protection must remain for genuine or uncertain structural changes, and its completion must be observed rather than inferred from a successful setter.

## Proposed implementation sequence and gates

1. **Fix protection semantics independently.** Subscribe before issuing hardware writes; distinguish already-correct state from a pending change; await matching readback/notification with a bounded timeout and device identity validation. Failed or uncertain protection must not permit destructive reconfiguration or restoration. Add callback/readiness evidence, while recognizing it does not alone prove source suppression. Correct the inaccurate lifetime-safety comments.
2. **Prototype persistent source taps.** Separate stable identity/format/output configuration from dynamic process membership. Keep configured sources present when their apps exit, if empty-source format behavior is supported. Update existing tap descriptions without replacing IDs. Preserve current per-source gain folding because one source can feed several mixes. Ordinary membership events must not enter aggregate teardown.
3. **Prefer static bundle subscriptions on macOS 26 if verified.** Configure source bundle IDs and the remainder's complementary exclusions, including BAM itself. Test helper identifiers: existing BAM matching accepts `target` and `target + "."` prefixes; Apple's native property is not documented as equivalent. Keep source and remainder filters disjoint. Process-list updates on older systems have a discovery race that must not be hidden behind a compatibility claim.
4. **Resolve transfer safety before shipping.** Updating a source and the remainder exclusion list requires separate writes. One ordering can duplicate audio; the other can leave it unassigned or briefly in the wrong gain path. Neither ordering is proven atomically safe. Do not solve this by unconditionally releasing mute, crossfading duplicated full-level paths, or merely waiting a fixed number of milliseconds.
5. **Only then handle structural edits.** Adding/removing configured source slots, changing devices, sample rates, permission state or recovery may still require separately protected reconfiguration. Live TapList mutation needs an explicit channel-layout contract; it is not necessary for routine process lifetime with a fixed tap set.

If these gates cannot protect a configured app's **first sample**, investigate the persistent virtual route. BAMDriver currently exposes eight slots, ignores client identity in Add/RemoveDeviceClient (`BAMDriver.c:882–919`), and supports only `ReadInput`/`WriteMix` (`:4174–4217`). Its slot gain is post-mix (`:4280–4311`). It cannot implement Background Music-style per-client attenuation unchanged: that needs client tracking, pre-sum processing, control publication and a persistent clock-managed output bridge.

## Validation must measure the bypass path

- Use a controlled output capture with external attenuation/dummy load, or a suitable off-ear headset fixture. Do not test failure paths on the user's ears at full hardware volume.
- Reproduce the actual gain relationship: high hardware gain, strongly attenuated configured source, and a differently attenuated remainder. Observe physical output, not only BAM meters or post-limiter counters.
- Cover first launch with immediate sound, helper-process launch, process exit/relaunch, rapid repeated churn, two sources joining/leaving together, membership-update failure, delayed hardware writes, no callbacks after successful start, permission loss, device reconnect and rate changes.
- For ordinary process lifetime, assert unchanged tap/aggregate IDs and zero stop/destroy/create calls; preserve callback format mapping, existing source gains and limiter state.
- Check no original-audio bypass, duplicate playback or wrong-channel gain. Failures must produce bounded silence rather than release unattenuated output. Also measure actual gaps and latency; callback processing time is not acoustic latency.
- Run model tests for delayed acknowledgements and failure ordering, then isolated Core Audio integration tests across supported OS versions. A new release requires this evidence, not another low-volume Calculator-only check.
